\section{End-to-end control flows}

The four sequence diagrams below share one convention: each column is a component, a solid arrow
is a call or message, a dashed arrow is a return value or response, and a grey box is local
processing.

\subsection{Inbound RPC (peer $\rightarrow$ us)}

\begin{figure}[H]
\centering
\begin{tikzpicture}
\seqactors{-5.6}{0/Peer, 4.2/RaftHandler, 8.4/RaftBehaviour, 12.6/RaftEngine}
\seqmsg{0}{4.2}{-0.85}{open substream, send \code{WireEnvelope}}

\seqmsg[seqret]{12.6}{8.4}{-3.7}{\code{Send \{ to: from \}}}
\seqmsg{8.4}{4.2}{-4.65}{\code{NotifyHandler::One}\\ \code{SendResponse}}
\seqmsg[seqret]{4.2}{0}{-5.3}{response frame, close substream}
\end{tikzpicture}
\caption{Inbound RPC: the reply travels on the \emph{same} substream that carried the request.}
\end{figure}

\begin{enumerate}[label=\arabic*., nosep]
  \item The peer opens an inbound substream; the handler reads the \code{WireEnvelope}.
  \item \code{ToBehaviour::Request} + \code{channel\_id}; a oneshot waits for the response.
  \item Behaviour: \code{PeerId} $\rightarrow$ \code{NodeId}; \code{inbound\_channels.insert}.
  \item \code{engine.handle\_rpc(from, msg, now)} $\rightarrow$ actions (usually a \code{Send} back to \code{from}).
  \item \code{execute\_actions} with \code{Some((from, channel\_id))} $\rightarrow$ \code{SendResponse} + \code{NotifyHandler::One}.
  \item The handler writes the frame and closes the unary substream.
  \item If the engine does not reply to \code{from}: the behaviour calls \code{remove(channel\_id)} to avoid a leak.
\end{enumerate}

\seqnote{8.4}{-5.25}{\code{pending.remove(cid)}}
\seqmsg{8.4}{12.6}{-5.95}{\code{handle\_rpc(to, msg)}}
\end{tikzpicture}
\caption{Outbound RPC: the response is matched to its request by \code{correlation\_id} (cid).}
\end{figure}

\begin{enumerate}[label=\arabic*., nosep]
  \item The engine emits \code{Action::Send}, or a \code{Broadcast} is fanned out.
  \item \code{send\_rpc}: map the peer, check connectivity, \code{pending.insert(correlation\_id)}.
  \item \code{NotifyHandler::Any} + \code{SendRequest}.
  \item The handler opens an outbound substream, writes and reads.
  \item \code{ToBehaviour::Response} $\rightarrow$ \code{pending.remove} $\rightarrow$ \code{handle\_rpc(pending.to, msg)}.
\end{enumerate}

Not connected: dial + \code{handle\_rpc\_failure} (lossy); the election/heartbeat tick retries later.

\begin{enumerate}[label=\arabic*., nosep]
  \item A follower's timeout expires $\rightarrow$ \code{tick} $\rightarrow$ it becomes a candidate.
  \item \code{Broadcast RequestVote} $\rightarrow$ the behaviour calls \code{send\_rpc} N times.
  \item Responses are matched by \code{correlation\_id}.
  \item Majority reached $\rightarrow$ \code{BecomeLeader}, initialise \code{next\_index}, start heartbeats.
\end{enumerate}

\begin{enumerate}[label=\arabic*., nosep]
  \item The app calls \code{propose} $\rightarrow$ the engine persists the entry.
  \item The engine emits replication actions $\rightarrow$ AppendEntries per follower (respecting \code{ae\_inflight}).
  \item \code{AppendEntriesResp} success $\rightarrow$ update \code{match\_index}.
  \item Majority reached $\rightarrow$ advance \code{commit\_index}, \code{Apply} $\rightarrow$ \code{Event::Committed}.
\end{enumerate}

\section{Module map of the crate}

\code{lib.rs} exports behaviour, handler, engine, protocol, storage and config. Suggested reading order:
\begin{enumerate}[label=\arabic*., nosep]
  \item \code{raft/types.rs}
  \item \code{engine.rs} --- tick, election, AE
  \item \code{behaviour.rs} --- \code{execute\_actions}, \code{poll}
  \item \code{handler.rs} --- unary I/O
  \item \code{storage/}, \code{raft/snapshot.rs} --- persistence and snapshots
  \item \code{bin/raft-node.rs} --- Swarm loop
\end{enumerate}

\section{Deliberate limitations and status}

\textbf{Implemented:} election over libp2p, replication, propose, commit events, chunked snapshot install, a multi-node example, engine tests without a Swarm.

\textbf{Missing / simplified:} AE pipeline $>$ 1; conflict-index optimisation; joint consensus; membership changes; a durable storage backend with an fsync contract (see Section~\ref{sec:storage}); metrics.

\begin{invariantbox}[Architectural thesis]
A pure Raft engine + libp2p Behaviour--Handler + unary multiplexed RPC is a viable composition; the adapter uses correlation IDs, a static peer map, deadline-driven ticks, and separates transport failure from membership.
\end{invariantbox}

\section{Conclusion}

This whitepaper describes in detail how \textbf{libp2p-raft} separates consensus from networking: \code{RaftEngine} upholds the Raft invariants; \code{RaftBehaviour} translates \code{Action}s into dials and handler events; \code{RaftHandler} executes unary framed RPCs over Yamux. The Swarm orchestrates everything without knowing about Raft. Within its simplified scope, the system is a laboratory for studying how a consensus state machine maps onto a modern P2P stack.
